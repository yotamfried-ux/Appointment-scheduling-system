# Strix scan of a local copy — 2026-10-21

Run: GitHub Actions "Strix security scan", run 4 on `main` (`aa051f8`), scan mode `standard`, against a throw-away local copy (local Supabase, production build, two seeded businesses). Production was not touched. The model was the one configured in the repository secrets.

**Result of the run:** the run was stopped by the 150-minute limit (exit "missing"), not finished by Strix. Strix had already reported findings. The job log keeps only the last 5000 lines, so **only VULN-0008 to VULN-0012 are readable from it**; VULN-0001 to VULN-0007 (if they exist) are in the uploaded artifact `strix-evidence-39668442814` (14 days) and have **not** been read by engineering yet. This file must be completed from the artifact.

| ID | Severity (Strix) | Finding | Status |
|---|---|---|---|
| VULN-0008 | High (7.3) | A customer is identified only by the phone number typed on the public form. Someone who knows a customer's number can use up that customer's booking and waitlist limits at one business and set the e-mail on the customer's record. Single business, needs the victim's number; the confirmation still goes to the address given on each booking. | **Open, product decision.** This is the trade-off of booking without an account (BKG-05). Real fixes are a one-time code to the phone (costs per message) or no longer merging by phone alone. Not changed. |
| VULN-0009 | Medium (4.3; Strix's own text says low) | A rejected value made the Data API return the whole failing row and the constraint name in the error detail. Only the caller's own row; no other business. | **Fixed:** migration `20261041000000_no_row_in_errors.sql` (five wrappers), pgTAP `230_no_row_in_errors.test.sql`. Checked: the unwrapped function still leaks the row, the wrapper returns no detail. |
| VULN-0010 | Medium (5.4) | A session that was logged out (or whose password was changed) kept working until its access token expired. Reproduced: with the asymmetric signing keys the token is verified locally, and the Auth server answers "session gone" only when asked. | **Fixed in the application:** `lib/auth/live-session.ts` asks the Auth server on every owner page, owner API call and owner action (a logged-out cookie is now refused: `scripts/security/08-…`, `tests/unit/live-session.test.ts`). **Not fixable here:** the Supabase Data API still accepts the old token directly until it expires; shorten "JWT expiry" in Supabase Auth settings (default 1 hour) if that matters. |
| VULN-0011 | Low (3.5) | No abuse controls on publishing a business: someone can name a business after a bank or authority and publish a booking page on our domain. | **Fixed 2026-10-22:** name screen at publication (held for an operator), operator kill switch, "report this business" link; migration `20261042000000_abuse_controls.sql`, pgTAP `240_abuse_controls.test.sql`, runbook `docs/runbooks/abuse.md`. |
| VULN-0012 | Medium (5.3) | Sign-up reveals whether an address is registered: (a) a repeated request differs, because only new addresses use the e-mail send quota; (b) the Auth endpoint itself answers `user_already_exists`. | **Partly fixed earlier** (`signUpAction` hides the error, PR 19). (b) is Supabase's own endpoint and (a) comes from its e-mail quota: not changed. Whether hosted Supabase answers like the local one is **not verified**; to check, sign up twice with one address on production. |

# Second run — 2026-10-22 (run 5, branch `claude/strix-round2-2026-10-22`)

Again stopped by the 150-minute limit. Readable from the job log (last 5000 lines): VULN-0004, 0006, 0013, 0016 to 0022 (the numbering restarted). The artifact `strix-evidence-39726599681` has the rest and has **not** been read. The model was the one in the repository secrets (the log does not name it).

| ID | Severity (Strix) | Finding | Status |
|---|---|---|---|
| 0004 | High (7.4) | **The second-factor gate read the factor list from the unsigned session cookie.** Deleting `user.factors` from the cookie made the gate see "no factor", and every owner page, export and write was open to someone who only knew the password. | **Fixed.** `lib/auth/live-session.ts` `checkSession`: the Auth server's own answer (`getUser`) decides whether a verified factor exists, and the signed token's `aal` says whether this session passed it. Control on the previous commit: the tampered cookie got 200 and read the customer list; now 401 / redirect to the code page (`scripts/security/09-mfa-cookie-tamper.mjs`, `tests/unit/live-session.test.ts`). Only accounts that enabled a second factor were exposed. |
| 0006 | High (7.4) | No limit on password guesses (about 600 a minute locally); also none on the six-digit code. | **Fixed in the application:** 10 sign-in attempts per e-mail per 10 minutes (`app/auth/actions.ts`), 10 code attempts per user per 5 minutes (`app/auth/mfa-actions.ts`); `scripts/security/10-login-rate-limit.mjs`. The Auth server's own per-address limit is a Supabase setting that was not checked on the hosted project. Trade-off: someone can make a known address wait 10 minutes by guessing at it. |
| 0018 | High (8.2) | Anyone who knows the default webhook secret of the **fake** billing provider can change any business's plan. | **A property of the scan setup, not of production:** the fake provider throws in production (`modules/billing/config.ts`) and the default secret exists only outside production. The scan workflow now sets a random `BILLING_WEBHOOK_SECRET`. Not changed: a forged event can move `last_event_at` a day ahead (needs the secret), and a rejected timestamp answers 500 instead of 4xx. |
| 0019 | Low (3.3) | The live-session check let a request through when the Auth server could not be reached. | **Fixed** with 0004: an unreachable Auth server now closes the owner area (nothing can be verified). |
| 0020 | Medium (4.3) | `export_audit` wrote export lines for a plan without the export feature. | **Fixed:** migration `20261043000000_export_audit_entitlement.sql`, pgTAP `250_export_audit_entitlement.test.sql`. |
| 0013, 0016 | Medium (6.5, 5.3) | Anyone who knows a customer's phone number can use up that customer's booking budget at one business (same as 0008). | **Open, owner decision** (a one-time code to the phone costs per message and adds a step). |
| 0017, 0021 | Medium, Low | A logged-out access token still works directly against the Data API until it expires; a used refresh token is not revoked as the setting suggests. | **Supabase settings, not code:** shorten "JWT expiry" and check "Detect and revoke compromised refresh tokens" in the Auth settings of the hosted project. The application itself now refuses a logged-out session (0010). |
| 0022 | Medium (4.3) | The customer's booking link (view) lets the page mint the cancel / reschedule / attend tokens. | **By design, not changed:** the link is the customer's way to manage the booking, like any magic link; it is `no-referrer`, `noindex`, and valid until a week after the appointment. A narrower design would need a second step (code or e-mail click). Say if you want it. |
