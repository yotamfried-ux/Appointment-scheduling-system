# Strix scan of a local copy — 2026-10-21

Run: GitHub Actions "Strix security scan", run 4 on `main` (`aa051f8`), scan mode `standard`, against a throw-away local copy (local Supabase, production build, two seeded businesses). Production was not touched. The model was the one configured in the repository secrets.

**Result of the run:** the run was stopped by the 150-minute limit (exit "missing"), not finished by Strix. Strix had already reported findings. The job log keeps only the last 5000 lines, so **only VULN-0008 to VULN-0012 are readable from it**; VULN-0001 to VULN-0007 (if they exist) are in the uploaded artifact `strix-evidence-39668442814` (14 days) and have **not** been read by engineering yet. This file must be completed from the artifact.

| ID | Severity (Strix) | Finding | Status |
|---|---|---|---|
| VULN-0008 | High (7.3) | A customer is identified only by the phone number typed on the public form. Someone who knows a customer's number can use up that customer's booking and waitlist limits at one business and set the e-mail on the customer's record. Single business, needs the victim's number; the confirmation still goes to the address given on each booking. | **Open, product decision.** This is the trade-off of booking without an account (BKG-05). Real fixes are a one-time code to the phone (costs per message) or no longer merging by phone alone. Not changed. |
| VULN-0009 | Medium (4.3; Strix's own text says low) | A rejected value made the Data API return the whole failing row and the constraint name in the error detail. Only the caller's own row; no other business. | **Fixed:** migration `20261041000000_no_row_in_errors.sql` (five wrappers), pgTAP `230_no_row_in_errors.test.sql`. Checked: the unwrapped function still leaks the row, the wrapper returns no detail. |
| VULN-0010 | Medium (5.4) | A session that was logged out (or whose password was changed) kept working until its access token expired. Reproduced: with the asymmetric signing keys the token is verified locally, and the Auth server answers "session gone" only when asked. | **Fixed in the application:** `lib/auth/live-session.ts` asks the Auth server on every owner page, owner API call and owner action (a logged-out cookie is now refused: `scripts/security/08-…`, `tests/unit/live-session.test.ts`). **Not fixable here:** the Supabase Data API still accepts the old token directly until it expires; shorten "JWT expiry" in Supabase Auth settings (default 1 hour) if that matters. |
| VULN-0011 | Low (3.5) | No abuse controls on publishing a business: someone can name a business after a bank or authority and publish a booking page on our domain. `docs/05` §5.11 prescribes a name screen, a "report" button and a kill switch; none exist. | **Open, product decision** (relevant before public sign-up, not for a closed pilot). Added to `open-decisions.md` as G-17. |
| VULN-0012 | Medium (5.3) | Sign-up reveals whether an address is registered: (a) a repeated request differs, because only new addresses use the e-mail send quota; (b) the Auth endpoint itself answers `user_already_exists`. | **Partly fixed earlier** (`signUpAction` hides the error, PR 19). (b) is Supabase's own endpoint and (a) comes from its e-mail quota: not changed. Whether hosted Supabase answers like the local one is **not verified**; to check, sign up twice with one address on production. |
