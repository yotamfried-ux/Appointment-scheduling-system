> מטרה: לגלות מראש מה יכול לקרות במערכת מהסוג הזה (כולל מקרי קצה ותקלות), ולתרגם כל תרחיש ל**החלטת תכנון** ול**ראיה שנדרשת**.
> שיטה (מתוך Engineering-OS: `patterns/testing/project-qualification.md`, `evidence-and-simulation.md`, `templates/booking-system`, `patterns/integrations/calendar` — Booking State Machine, `docs/troubleshooting/{database,payments,realtime}.md`):
> *capability × layer × evidence*. תרחיש הוא "ניתן לאימות" רק כשיש ראיה טרייה בשכבות שרמת הסיכון שלו דורשת. אין הופכים NOT TESTED / BLOCKED ל-PASS. מוק אינו ראיה לאינטגרציה.

## 0. איך משתמשים בקטלוג

- **מזהה** (`BKG-04`) — משמש בשמות בדיקות, בשמות קבצי סימולציה ובדוח ה-qualification.
- **P0** = חייב לפני השקה (אובדן כסף/נתונים, דליפת דיירים, double-booking). **P1** = חוויית ליבה. **P2** = איכות/צמיחה.
- **שכבה:** `U` unit · `D` DB/SQL (pgTAP, RLS, אילוצים) · `I` אינטגרציה על Postgres אמיתי · `C` contract/webhook · `E` E2E Playwright על Preview · `S` סימולציית persona · `F` הזרקת תקלה · `X` אבטחה · `A` נגישות/ביצועים.
- עמודת **החלטה** = מה התרחיש מחייב בארכיטקטורה (ומופיע בסעיף 9 כשינויים שנכנסים לתוכנית).
- חלק מהתרחישים תלויים בהחלטות שלך (סעיף 10) ומסומנים 🔶.

## 2. מכונת מצבים של תור (מקור אמת)

```
                ┌────────────── (אישור ידני נדרש) ──────────────┐
 [נוצר] ──► PENDING_APPROVAL ──approve──► CONFIRMED ──► COMPLETED
    │              │ reject/expire              │  ├──► NO_SHOW
    │              ▼                            │  ├──► CANCELLED_BY_CUSTOMER
    └─(אוטומטי)─► CONFIRMED                     │  ├──► CANCELLED_BY_BUSINESS
                                                │  ├──► CANCELLATION_REQUESTED ──approve──► CANCELLED_BY_CUSTOMER
                                                │  │                          └─reject───► CONFIRMED
                                                │  └──► RESCHEDULED*  (= תור חדש + קישור `rescheduled_from`; הישן נסגר)
```

- מעבר חוקי נקבע בטבלת `allowed_transitions` אחת, נאכף ב-DB (טריגר) וגם ב-service. מצבי קצה (`CANCELLED_*`, `COMPLETED`, `NO_SHOW`) סופיים; תיקון = פעולת "החזרה" מתועדת של בעלים בלבד (`NO_SHOW→CONFIRMED` אם סומן בטעות).
- **כל מעבר** נרשם ב-`appointment_transitions` (מי, מתי, ערוץ, סיבה). מעבר מתבצע ב-commit לפני תופעות לוואי (אימייל, יומן, waitlist) — תופעות הלוואי נשלחות דרך outbox עם retry.
- Idempotency: אותו מעבר פעמיים (לחיצה כפולה, שליחה חוזרת של webhook) = no-op, לא שגיאה.
- *שינוי מועד* מומש כתור חדש + סגירת הישן באותה טרנזקציה — כך האילוץ נגד חפיפה נשמר ואין "חלון ריק" שבו הלקוח מאבד את התור.

## 4. תרחישי קצה בין-תחומיים (שרשראות)

אלה תרחישים שבהם כמה מודולים מתנגשים — הם מקור הבאגים בפועל:

1. **ביטול ← waitlist ← הצעה ← קבלה ← יומן ← הודעות** (CXL-01 + WLT-01..04 + CAL-04 + NTF-03): כל החוליות דרך outbox; בדיקת E2E אחת מקצה לקצה עם כשל מכוון בכל חוליה.
2. **בעלים משנה זמינות ← תורים מושפעים ← הודעות ללקוחות** (AVL-07 + RSC-04 + NTF-*): פעולה אחת יוצרת N מעברי מצב והודעות; חייבת preview, אישור, ו-bulk idempotent.
3. **מנוי פג ← הזמנות פתוחות ← תורים קיימים ← תזכורות** (BIL-01 + BKG-11 + NTF-01): תורים שכבר נקבעו **חייבים** להמשיך לקבל שירות (לא מענישים לקוחות קצה על חוב של העסק).
4. **שינוי שירות (משך) ← תורים קיימים ← חפיפה** (CAT-04 + AVL): snapshot מונע התנגשות רטרואקטיבית.
5. **DST בלילה ← תזכורות 9:00 ← יום ריק ← סיכום בעלים** (AVL-03 + NTF-01/11).

## 6. מה משתנה בתוכנית (שינויים שנכנסים למסמך 03)

1. **`appointment_transitions` + `allowed_transitions`** + מכונת מצבים מפורשת (סעיף 2).
2. **Outbox/`domain_events` + `job_runs` + `notification_log` unique** כתשתית ליבה — לפני מודול ההודעות (שלב 6 → תשתית כבר בשלב 2).
3. **Snapshot** של שירות בתור (שם, משך, מחיר, חיץ) — `appointments.service_snapshot jsonb`.
4. **`slot_holds`** (החזקה זמנית) כחלק משלב 4.
5. **`Clock` port** בכל לוגיקת זמן + ספריית tz אחת.
6. **`Idempotency-Key`** לכל mutation ציבורי.
7. **`suppressions`** לאימייל, **`approval_deadline`**, **`accepting_bookings`** נגזר מ-entitlements.
8. **schema-lint ב-CI**: כל טבלה ב-`public` חייבת RLS; כל טבלה עם `business_id` חייבת אינדקס מוביל.
9. **`metrics` module** יחיד להגדרות מדדים.
10. **Admin back-office** מינימלי (חיפוש עסק, override entitlement, צפייה מבוקרת) — שלב 9.
11. סולם נאמנות לכל תרחיש P0: לפחות שכבה אחת בנאמנות **DB אמיתי** ושכבת **E2E על Preview**, לא מוקים בלבד.
